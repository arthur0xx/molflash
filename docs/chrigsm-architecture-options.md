# خيارات البنية السحابية لـ ChriGsm

**الحالة:** توصية معمارية أولية بانتظار موافقة المالك قبل بدء الترحيل.

## متطلبات النظام

يحتاج ChriGsm إلى متجر خدمات رقمية ولوحة CMC ومنطقة عميل تعمل على بيانات موحدة. تشمل البيانات المنتجات والتصنيفات، الطلبات وحالاتها، بيانات الإدخال الديناميكية لكل خدمة، أرصدة المحافظ وسجلها غير القابل للتعديل، الرسائل والدعم، وأصول الصور. كما يجب أن يرى العميل ومشرف CMC تغيّر حالة الطلب والرصيد والمنتجات فورًا عند الحاجة.

## ما تؤكده المصادر الرسمية

Cloud Firestore يوفّر مستمعات فورية عبر `onSnapshot()` للمستندات والاستعلامات؛ يجلب المستمع أول لقطة حالية ثم يرسل لقطة جديدة عند كل تغيير. وتشير الوثائق أيضًا إلى أن الكتابات المحلية تُشعِر المستمعات فورًا، مع إمكانية تمييز الكتابات غير المرسلة بعد عبر `metadata.hasPendingWrites`. [1]

توفّر MongoDB Atlas طبقة M0 مجانية دائمة بسعة 512 ميغابايت وموارد مشتركة؛ وتذكر وثائق Atlas أن الطبقات المجانية مخصصة لبيئة تطوير صغيرة وأنها لا تنتهي، مع خصائص محدودة مقارنة بالطبقات المدفوعة. [2] [3]

## مقارنة موجّهة لمتجر ChriGsm

| معيار التشغيل | Firebase: Auth + Firestore + Storage | MongoDB Atlas + API مستقل |
|---|---|---|
| الحسابات والصلاحيات | مصادقة جاهزة وقواعد وصول مرتبطة بالهوية | يحتاج بناء أو دمج خدمة مصادقة منفصلة |
| تحديث حالة الطلب والرصيد | مستمعات فورية جاهزة في الواجهة | يحتاج API، ثم polling أو WebSocket/Change Streams |
| الصور | مساحة تخزين ضمن المنظومة نفسها | يحتاج خدمة ملفات إضافية مثل S3 أو Cloudinary |
| الحقول الديناميكية | تُحفظ ككائنات أو مصفوفات داخل وثائق المنتج والطلب | تُحفظ طبيعيًا كوثائق JSON مرنة |
| محفظة العميل | تحتاج مسار خادم موثوق ومعاملات Firestore | تحتاج مسار خادم موثوق ومعاملات وسجل محاسبي |
| ملاءمة Vercel الحالي | ممتازة: واجهة Vercel مع API Serverless وFirebase | جيدة: واجهة/API Vercel مع اتصال Atlas |
| التشغيل الأولي المجاني | مناسب جدًا للمرحلة الأولى مع مراقبة حدود الاستخدام | مناسب للتطوير، لكن يتطلب خدمات إضافية ليصبح متكاملًا |

## التوصية الأولية

**يوصى بـ Firebase** كمنظومة أساسية في النسخة التالية، مع إبقاء Vercel لاستضافة واجهة React ووظائف API الخلفية. السبب هو أن ChriGsm يحتاج ترابطًا فوريًا بين المتجر ولوحة CMC ومنطقة العميل، بالإضافة إلى حسابات وصور ورسائل، وهذه خدمات يوفرها Firebase ضمن حل واحد بدل تجميع مصادقة وقاعدة بيانات وتخزين وتحديثات فورية من عدة مزودين.

لا يعني ذلك منح المتصفح صلاحية تغيير كل شيء مباشرة. تُقسم العمليات إلى طبقتين:

| نوع العملية | مسار التنفيذ |
|---|---|
| عرض الكتالوج وحالة طلب العميل ورسائله | Firestore مع قواعد قراءة مقيدة، ومستمعات فورية عند الحاجة |
| إنشاء طلب عادي وإرسال حقول الخدمة | API على Vercel يتحقق من السعر وحالة المنتج ثم ينشئ الطلب |
| تغيير الرصيد، اعتماد/رفض الطلب، كود التسليم، تغيير السعر أو التصنيف | API إداري موثوق فقط باستخدام Firebase Admin؛ لا تُمنح من المتصفح مباشرة |
| رفع صورة منتج أو أيقونة تصنيف | Firebase Storage عبر رابط موقّع أو تدفق تحقق خادمي |

## نموذج البيانات المقترح

| مجموعة البيانات | الحقول الجوهرية | علاقتها |
|---|---|---|
| `users` | `uid`, `role`, `name`, `phone`, `walletBalance`, `status` | عميل أو مدير CMC |
| `categories` | `name`, `slug`, `icon`, `sortOrder`, `isActive` | تصنيف واحد يضم عدة منتجات |
| `products` | `categoryId`, `title`, `priceMad`, `dynamicFields`, `deliveryType`, `image`, `isActive` | يعرض في المتجر ويُنسخ كسجل إلى الطلب |
| `orders` | `customerId`, `productSnapshot`, `submittedFields`, `status`, `delivery`, `timeline` | مرتبط بعميل ومنتج وسجل محفظة |
| `walletTransactions` | `customerId`, `type`, `amountMad`, `reference`, `createdAt` | سجل محاسبي مصدر الحقيقة للرصيد |
| `supportConversations` | `customerId`, `orderId`, `messages`, `channel` | يربط الدعم بالعميل أو الطلب |
| `settings` | `currency`, `supportChannels`, `storeStatus` | إعدادات تشغيل موحّدة |

## ضوابط إلزامية

لا يُخزن رصيد المحفظة كقيمة يستطيع العميل تعديلها. كل تعديل ينشئ سجلًا في `walletTransactions` وتُحدَّث القيمة المجمعة في معاملة خادمية. لا يُظهر كود التسليم في مستند مقروء عموميًا؛ يعيده مسار خادمي بعد التحقق من مالك الطلب. ولا تستخدم مفاتيح Firebase الإدارية في متصفح العميل أو في مستودع Git.

## إضافة: NocoDB كخيار ثالث

NocoDB ليس قاعدة بيانات تطبيقية مُدارة مثل Firestore ولا بديلًا مباشرًا عن MongoDB Atlas؛ هو واجهة لا-كود/لو-كود لإدارة بيانات منظمة وإجراء عمليات CRUD وعرضها على شكل جداول أو Kanban أو نماذج. يمكن أن يفيد كلوحة داخلية مؤقتة لفريق التشغيل، لكنه لا يصلح وحده كمنظومة خلفية موثوقة لمحفظة العملاء أو أكواد التسليم أو صلاحيات المتجر الدقيقة.

| جانب المقارنة | NocoDB | Firebase | MongoDB Atlas |
|---|---|---|---|
| الدور الطبيعي | واجهة بيانات وتشغيل داخلية | باك-إند متكامل وبيانات فورية | قاعدة بيانات مُدارة تحتاج باك-إند وخدمات مساندة |
| قيمة CMC | يمكن أن يسرّع جداول الطلبات والمنتجات يدويًا | يمكن بناء CMC مخصّصة على بيانات حية | يمكن بناء CMC مخصّصة عبر API |
| المحفظة وأكواد التسليم | لا يُعتمد عليه مباشرة كطبقة أسرار أو معاملات مالية | يدعم مسارات خادمية موثوقة ومعاملات | يدعم من خلال API ومعاملات MongoDB |
| التحديث الفوري للمتجر والعميل | Webhooks حسب الجدول، لا بديل عن واجهة العميل الحية | مستمعات فورية مدمجة | يحتاج WebSockets أو مسار تحديث منفصل |
| الاستضافة المجانية | مجانية عند الاستضافة الذاتية لكن تتطلب خادمًا مستمرًا | سحابية مُدارة للبدء | طبقة M0 مُدارة مجانية للتطوير |

تؤكد وثائق NocoDB أن النسخة المجتمعية ذاتية الاستضافة مجانية للاستخدام الداخلي، لكنها تتطلب على الأقل 2 vCPU و2GB RAM و10GB قرصًا، وتوصي للإنتاج بـ4 vCPU و8GB RAM و50GB+؛ لذلك لا تتوافق عمليًا مع هدف الاستضافة المجانية الدائمة دون خادم مستقل. [4]

> التوصية: لا نستخدم NocoDB كقلب التطبيق. يمكن إضافته لاحقًا كأداة تشغيل داخلية اختيارية إذا وفّرنا خادمًا دائمًا، بينما يظل Firebase الحل الأنسب ليكون مصدر البيانات الموحد للمتجر وCMC والعميل.

[4]: https://nocodb.com/docs/self-hosting "NocoDB — Self-hosting"

## مقارنة طبقة التطبيق: React/Vite وNext.js وNestJS

| التقنية | موضعها الصحيح | المزايا لمشروع ChriGsm | التكلفة/المقايضة |
|---|---|---|---|
| React + Vite | واجهة SPA منفصلة | قاعدة الكود الحالية موجودة، تطوير سريع، ونشر سهل على Vercel. Vite ينتج `dist` ثابتًا ويدعم معاينات Git على Vercel مباشرة. [5] | يبقى تنفيذ SEO وعرض صفحات الخدمة للمحركات وطبقة API الآمنة منفصلين؛ ستحتاج Firebase SDK ومسارات Vercel Functions أو API مستقل |
| Next.js | React للواجهة ومسارات الخادم في مشروع واحد | يجعل صفحات الخدمات والكتالوج قابلة للعرض الخادمي، ويضع Route Handlers للطلبات والمحفظة والويبهوكس قرب الواجهة. Route Handlers تدعم HTTP methods وتعمل وقت الطلب للبيانات الحساسة. [6] | يتطلب ترحيل واجهة Vite الحالية وإتقان حدود Server/Client Components والكاش |
| NestJS | خادم API مستقل، وليس بديلًا للواجهة | مناسب عندما تتوسع عمليات الطلبات والمحافظ وWhatsApp والموظفين إلى وحدات كثيرة وفريق خلفي. يوفر بنية خادم TypeScript منظمة وقابلة للاختبار والتوسع. [7] | خادم منفصل واستضافة وتشغيل ومراقبة أكثر؛ غير ضروري في النسخة الأولى المعتمدة على Firebase وVercel |

## توصية طبقة التطبيق

يُقترح **Next.js + Firebase** للمرحلة التالية، وليس React/Vite + NestJS. وهو يوازن بين تجربة الهاتف الحالية والصفحات العامة القابلة للفهرسة ومسارات API الآمنة من داخل مشروع واحد منشور على Vercel. تحفظ واجهات المتجر وCMC ومنطقة العميل في قاعدة React واحدة؛ فيما تنفذ Route Handlers عمليات الإدارة والمحفظة والتسليم وتستدعي Firebase Admin فقط على الخادم.

يبقى **NestJS خيار مرحلة توسع**، لا مرحلة البداية. نضيفه فقط إذا ظهرت حاجة مؤكدة إلى عمال خلفية دائمة، أو WebSockets مخصصة، أو تدفقات WhatsApp كثيفة، أو فريق Backend مستقل. وحتى ذلك الحين، لا ينبغي بناء خادمين لنفس منطق الطلبات.
