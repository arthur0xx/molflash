# خطة التعامل الآمن مع حسابات الاختبار قبل الإطلاق العام

**الحالة:** قرار وتنفيذ مؤجلان؛ هذا المستند لا يعطّل أو يحذف حسابًا أو وثيقة.  
**النطاق:** Firebase Authentication وFirestore في مشروع `chrigsm-4f883`.  
**تاريخ المراجعة:** 14 أغسطس 2026، بتوقيت Africa/Casablanca.

## الملخص التنفيذي

أظهر الجرد القراءة فقط وجود **حسابين** في Firebase Authentication، وكلاهما ضمن نطاق الاختبار `@chrigsm.test`. كما توجد **ثلاث** وثائق عملاء تحمل علامة `demo: true` في Firestore، وخمسة طلبات ظاهرة على الأقل؛ لذا فإن حذف حساب مصادقة وحده ليس تنظيفًا كاملاً وقد يترك بيانات تشغيلية يتيمة. لا ينبغي تنفيذ حذف الآن، خصوصًا مع غياب اعتماد Firebase Admin من بيئة العمل المعاد ضبطها وعدم وجود نسخة تشغيلية متحقق منها.

> القرار الافتراضي الآمن هو **التعطيل المؤقت** للحسابات التجريبية بعد موافقة المالك، ثم تنفيذ جرد خادمي قراءة فقط يربط كل UID بوثائق العميل والطلبات والمحفظة والدعم وسجل التدقيق. لا يبدأ الحذف النهائي إلا بعد وجود manifest مراجع ونسخة انتقالية صالحة واختيار سياسة للاحتفاظ بسجل الطلبات.

المصدر المباشر للنتائج هو Firebase Console أثناء هذه المراجعة. لم تُفتح قوائم الحذف أو التعطيل ولم تعرض كلمات مرور أو رموز أو مفاتيح.

## 2. المخاطر التي تمنع الحذف الآن

| الخطر | الأثر | الإجراء الوقائي |
|---|---|---|
| حذف Authentication فقط | قد تبقى وثائق العملاء والطلبات والمحافظ والدعم وسجل التدقيق بلا مالك. | أنشئ manifest بالـUID و`customerId` وكل عدد تبعيات قبل أي تغيير. |
| حذف وثائق Firestore من المتصفح | قد يتجاوز مسارًا مدققًا أو يترك سجلات ناقصة، كما أن القواعد تمنع الكتابة المباشرة الحساسة أصلًا. | استخدم سكربت خادمي مراجع، بخيار `--dry-run` أولًا، ومن دون حذف صامت. |
| غياب نسخة تشغيلية متحقق منها | لا يمكن التراجع عن حذف بيانات مرتبطة أو تشخيص ما كان موجودًا. | نفذ نسخة انتقالية قراءة فقط وmanifest وSHA-256 ثم تحقق داخل Firebase Emulator. |
| خلط التجريبي بالحقيقي | قد يؤدي إلى حذف أول عميل أو طلب حقيقي عند الإطلاق. | استخدم معيارًا مزدوجًا: `demo: true` **و** مراجعة المالك للمحتوى والتاريخ، لا الاسم أو النطاق فقط. |
| فقدان حساب المدير الوحيد | قد يمنع الوصول إلى CMC إذا لم يوجد مدير بديل يملكه المالك. | لا تعطّل `admin-demo` قبل التحقق من وجود حساب مدير مملوك للمالك واختبار دخول CMC به. |

## 3. مسار التنفيذ المقترح

### المرحلة أ: تجميد الاختبارات دون حذف

بعد موافقة المالك الصريحة، يعطّل حسابا Authentication التجريبيان (`admin-demo` و`cus-yassine`) بدل حذفيهما. التعطيل يمنع تسجيل الدخول ويمكن عكسه أثناء التحقق؛ أما الحذف فهو عملية منفصلة لاحقة. تدعم Firebase إدارة مستخدم مخصص كحساب معطّل أو حذفه بالـUID من بيئة خادمية موثوقة. [1]

بوابة القبول لهذه المرحلة هي فشل دخول الحسابين التجريبيين، واستمرار دخول حساب المدير المملوك للمالك إلى CMC، وعدم تغير عدد وثائق Firestore أو الطلبات أو قيود المحفظة.

### المرحلة ب: manifest ونسخة انتقالية

قبل أي حذف نهائي، ينفذ سكربت Firebase Admin **قراءة فقط** من بيئة لا تعيد ضبط الأسرار، وينتج ملفًا خاصًا خارج Git. يسجل لكل معرف تجريبي: UID والبريد المختصر والدور والعلامة التجريبية ومعرف العميل وعدد الطلبات وقيود المحفظة وتذاكر الدعم وسجلات التدقيق. لا يسجل كلمات مرور أو رموز جلسة أو أسرار أو محتوى نماذج الطلبات.

يُرفق manifest بلقطة JSON للبيانات المحددة وSHA-256، ثم ينجح اختبار قراءة اللقطة في Firebase Emulator. الخطة بلا فوترة؛ لا تُدّعى نسخ Firestore المدارة. توضح Firestore أن النسخ المدارة والاستعادة تتطلبان Blaze وتترتب عليهما تكلفة تخزين/استعادة، والاستعادة المدارة تكتب إلى قاعدة جديدة. [2] [3]

### المرحلة ج: قرار الاحتفاظ

يختار المالك واحدًا من المسارين، ولا يخلط بينهما:

| القرار | ما يبقى | ما يزال ممنوعًا | الاستخدام المناسب |
|---|---|---|---|
| **تنظيف بيتا محافظ** | وثائق الطلبات وسجل التدقيق التجريبي مع وسم واضح؛ حسابات الدخول معطلة فقط. | حذف Authentication أو Firestore. | إذا كان المالك يريد الاحتفاظ بدليل التحقق قبل أول بيانات حقيقية. |
| **تنظيف إطلاق نهائي** | manifest والنسخة الخاصة فقط، وسجل احتفاظ مختصر يوافق عليه المالك. | تنفيذ الحذف قبل اجتياز اختبارات sandbox وdry-run. | بعد تأكيد أن كل البيانات التجريبية غير مطلوبة. |

### المرحلة د: الحذف النهائي بعد قرار مستقل

لا ينفذ هذا المسار تلقائيًا. بعد موافقة واضحة على قائمة manifest محددة، ينفذ سكربت خادمي مراجع بالترتيب التالي: جرد `--dry-run`، اختبار Firebase Emulator، تعطيل الحسابات، تحقق من عدم تسجيل الدخول، معالجة تبعيات Firestore بمعرف العميل، ثم حذف Authentication وFirestore بالدفعات المراجعة وإخراج تقرير نجاح/فشل. لا تستخدم عملية حذف جماعي تخفي فشل سجل بعينه؛ تسجل نتيجة كل UID ومعرف وثيقة.

إذا كانت هناك وظيفة حذف مستقبلية، فالحذف الدفعي في Firebase Admin لا يشغّل معالجات `onDelete` لكل مستخدم، لذا يلزم اعتماد طريقة الحذف على تدفقات المشروع الفعلية بدل افتراض تنظيف تلقائي. [1]

## 4. قرارات المالك المطلوبة

| القرار | الخيارات | الأثر | الحالة المطلوبة |
|---|---|---|---|
| مدير بديل مملوك | إنشاء/تأكيد حساب مدير حقيقي، ثم اختبار CMC. | يمنع فقدان الوصول عند تعطيل `admin-demo`. | مطلوب قبل تعطيل حساب المدير التجريبي. |
| وضع الاختبار | تعطيل فقط أو حذف نهائي. | يحدد ما إذا كانت الحسابات قابلة للعكس. | مطلوب قبل أي تعديل في Authentication. |
| سياسة الوثائق التجريبية | احتفاظ مؤقت أو حذف نهائي بعد manifest. | يحدد معالجة العملاء غير المرتبطين والطلبات والسجلات. | مطلوب قبل أي حذف Firestore. |
| النسخ | انتقال يدوي متحقق أو Blaze للنسخ المدارة. | يحدد درجة الاسترداد قبل حذف أو إطلاق تجاري. | مطلوب قبل حذف نهائي أو إطلاق عام. |
| قالب البريد | اعتماد الافتراضي أو معالجة قيد Firebase لاحقًا. | لا يوقف الاستعادة لكنه يؤثر على تجربة الإطلاق. | قرار مستحسن قبل الإعلان العام. |

## 5. معايير إغلاق ما قبل الإطلاق

لا تعتبر هذه المهمة مكتملة للإطلاق العام حتى تتوفر نسخة انتقالية متحقق منها، وmanifest موقع بالمراجعة، وحساب مدير مملوك للمالك تم اختباره، وقرار مكتوب للحسابين التجريبيين والوثائق الثلاث التجريبية. بعد أي تغيير، يعاد اختبار الزائر والعميل والمدير، مع التحقق من أن العميل لا يقرأ إلا بياناته وأن CMC لا يقبل إلا المدير.
