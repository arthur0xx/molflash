# تصميم إثبات التحويل اليدوي — 2026-08-18

## القرار التشغيلي

بعد أن ينشئ العميل تحويلًا يدويًا ويرى تعليمات الوسيلة ورقم RIB والمرجع الفريد، يستطيع إرفاق **صورة واحدة لإثبات التحويل** بصيغة PNG أو JPEG أو WebP وحجم لا يتجاوز 10 ميغابايت. لا يُضاف رصيد ولا يبدأ تنفيذ الطلب بمجرد رفع الصورة؛ يظل القرار النهائي للمالك بعد مطابقة مبلغ العملية ومرجع `CHR-…` والحساب البنكي.

لا يُخزن رابط إثبات عام في Firestore. يرفع العميل الملف إلى Cloudinary ضمن أصل من نوع `authenticated` في مسار مقيّد `chrigsm/payment-proofs/<paymentReference>`، ثم تحفظ وثيقة `payments` المعرف الداخلي والتوقيت والبيانات التقنية الدنيا فقط. يسترجع المالك الصورة عبر مسار إداري خادمي يتحقق من رمز Firebase ودور المالك قبل تسليمها. لا يرى العميل إثبات أي عميل آخر، ولا يمكنه الوصول إلى CMC أو إلى أصل إثبات غير تابع له.

## نموذج البيانات

| الحقل | الغرض | جهة الكتابة |
|---|---|---|
| `status: proof_submitted` | يثبت أن العميل أرفق إثباتًا وينتظر مراجعة المالك | مسار العميل الخادمي فقط |
| `proofPublicId` | معرّف Cloudinary المقيّد، من دون رابط عام | مسار العميل الخادمي فقط |
| `proofSubmittedAt` | وقت قبول الإثبات | الخادم |
| `proofContentType` | نوع الصورة المقبول | الخادم بعد التحقق |
| `proofSizeBytes` | حجم الصورة المقبول | الخادم بعد التحقق |
| `reconciliationNote` | ملاحظة داخلية للمالك عند المطابقة أو الرفض | مسار مراجعة المالك فقط |

## تدفق العميل

1. ينشئ العميل التحويل من سعر محفوظ خادميًا ويستلم المرجع والتعليمات.
2. يختار صورة الإيصال؛ لا يسمح الرفع إلا لصاحب العملية، في حالة `manual_transfer_pending`، وقبل انتهاء المرجع.
3. يحصل العميل على توقيع رفع قصير العمر لمعرف محدد لا يمكنه اختياره.
4. بعد نجاح رفع Cloudinary المقيّد، يستدعي مسار تثبيت الإثبات. يتحقق الخادم من الملكية والحالة والمعرف والنوع والحجم ثم ينقل الحالة إلى `proof_submitted` ويسجل أثر تدقيق.
5. تعرض منطقة العميل أن الإثبات أرسل للمراجعة؛ لا يسمح باستبداله بعد التثبيت.

## تدفق المالك

1. يظهر تبويب الدفع في CMC عدادًا واضحًا لإثباتات التحويل الجديدة.
2. يفتح المالك الإثبات عبر مسار محمي، ويراجع المرجع والمبلغ والوسيلة ونوع العملية ووقت الإرسال.
3. بعد مراجعة الحساب البنكي، يؤكد العملية مع ملاحظة مطابقة اختيارية؛ فقط حينها تشحن المحفظة أو يصبح الطلب `processing` ضمن معاملة Firestore واحدة.
4. عند الرفض، تبقى الصورة وسجل المراجعة لأثر التدقيق؛ لا يحذف السجل المالي.

## إشعار WhatsApp

سيُضاف حدث داخلي ثابت باسم `payment_proof_uploaded` يستخدم فقط طبقة Meta WhatsApp Business Cloud API الحالية عندما تكون كل الإعدادات والقالب المعتمد موجودة. لا يستدعي التطبيق أي API ولا يدّعي نجاح الإشعار عندما `WHATSAPP_ENABLED` ليس `true` أو حين ينقص رقم الأعمال أو رمز الوصول أو قالب إشعار المالك. في هذه الحالة، يظل إشعار CMC الحقيقي متاحًا عبر حالة الدفعة وقائمة الإثباتات.

| الخيار | النتيجة | الإعداد المطلوب |
|---|---|---|
| إشعار CMC فقط | تظهر العملية فورًا في مركز الدفع للمالك | لا إعداد خارجي |
| إشعار CMC + WhatsApp رسمي | تظهر العملية في CMC ويرسل قالب Meta للمالك مرة واحدة لكل إثبات | إعداد Meta Business، قالب معتمد، وأسرار خادمية في Vercel |

## ضوابط القبول

- لا تُقبل صورة من عميل آخر أو لعملية منتهية/مؤكدة/مرفوضة.
- لا تظهر أي صورة إثبات برابط عام أو ضمن لقطة عامة.
- لا يمكن للعميل تعديل الرصيد أو حالة التأكيد أو ملاحظة المطابقة.
- لا يعتمد الدفع تلقائيًا، ولا يكفي رفع صورة أو وجود المرجع وحده.
- اختبار Firestore يثبت عزل `payments` بين العملاء ومنع الكتابة المباشرة.
- يجتاز `lint` و`test:firestore-rules` و`build` قبل معاينة Vercel.

## مصدر قرار حماية الأصل

راجعت وثائق Cloudinary الرسمية في 2026-08-18. تؤكد أن أصول `authenticated` تتطلب رابط تسليم موقّعًا للوصول إلى الأصل أو المشتقات، وأن سر API يجب ألا يدخل المتصفح. لذلك يحفظ التطبيق معرّف الأصل فقط ويولّد رابط العرض للمسؤول من مسار خادمي محمي. المصدر: https://cloudinary.com/documentation/control_access_to_media وhttps://cloudinary.com/documentation/delivery_url_signatures
