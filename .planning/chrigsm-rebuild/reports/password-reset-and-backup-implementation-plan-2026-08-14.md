# خطة التنفيذ الدقيقة: استعادة كلمة المرور والنسخ الاحتياطي لـChriGsm

**حالة الخطة:** جاهزة للتنفيذ، ولم يُطبق أي تغيير من هذه الوثيقة بعد.  
**النطاق:** Next.js 16 + Firebase Authentication + Firestore + Vercel، مع الالتزام الحالي بعدم تفعيل فوترة من دون قرار صريح من المالك.

> **القرار المعماري الأساسي:** استعادة كلمة المرور لا تحتاج قاعدة بيانات إضافية ولا API خادميًا ولا سرًا جديدًا؛ Firebase Authentication يرسل رسالة الاستعادة نفسها. أما النسخ الاحتياطي التلقائي الكامل لـFirestore فيحتاج عمليًا إلى تفعيل الفوترة لأن النسخ الاحتياطي المدار والتصدير إلى Cloud Storage يتطلبان خطة Blaze. لذلك يجب فصل تنفيذ استعادة كلمة المرور الآن عن قرار النسخ الاحتياطي التلقائي المدفوع لاحقًا.

---

## 1. ما سنبنيه لاستعادة كلمة المرور

### النتيجة للمستخدم

سيظهر رابط **«نسيت كلمة المرور؟»** في صفحة الدخول. يفتح الرابط نموذجًا بسيطًا لإدخال البريد المرتبط بالحساب. بعد الإرسال، تظهر رسالة عامة لا تكشف ما إذا كان البريد مسجلًا أم لا، مثل:

> «إذا كان البريد مرتبطًا بحساب ChriGsm، ستصلك رسالة لإعادة تعيين كلمة المرور خلال دقائق.»

سيصل البريد من Firebase Authentication، ويحتوي رابطًا يعيد المستخدم إلى صفحة ChriGsm المناسبة بعد إتمام العملية. في إعدادات الحساب سيستبدل الزر المعطل **«إرسال رابط التغيير»** بزر عامل يستخدم البريد المرتبط بالحساب؛ لا يحتاج العميل إلى إدخال بريد آخر.

Firebase يوفر `sendPasswordResetEmail` لهذا التدفق، ويمكن تخصيص قالب الرسالة ولغتها ورابط العودة من Firebase Console. يجب إدخال أي نطاق يعود إليه المستخدم ضمن Authorized Domains. [1] [2]

### التغييرات الدقيقة في الشفرة

| الترتيب | الملف أو الإعداد | التغيير البرمجي |
|---:|---|---|
| 1 | `src/lib/demo-auth.ts` | إضافة دالة `requestPasswordReset(email, continuePath?)` تستخدم استيرادًا ديناميكيًا لـ`sendPasswordResetEmail` و`firebaseServices()`؛ بذلك يستمر فصل Firebase عن حزمة المتجر العامة. |
| 2 | `src/lib/demo-auth.ts` | توحيد البريد عبر `normalizedEmail()` حتى يقبل المستخدم رقم الهاتف التجريبي أو البريد في صفحة الدخول، مع اقتصار الاستعادة الفعلية على البريد النهائي. |
| 3 | `src/components/login-form.tsx` | إضافة رابط «نسيت كلمة المرور؟» وحالة بسيطة داخل الصفحة أو نموذج صغير: `resetMode`، حقل بريد، `submittingReset`، ورسالة نجاح عامة. لا يظهر الخطأ `auth/user-not-found` للمستخدم لأن ذلك يسمح بتعداد الحسابات. |
| 4 | `src/components/account-console.tsx` | استبدال زر كلمة المرور المعطل بزر حقيقي. يستدعي الدالة بالبريد الموجود في `profileDraft.email` أو البريد الموثق من الجلسة، ويعرض نجاحًا عامًا لا يكشف تفاصيل حساسة. |
| 5 | `src/app/login/page.tsx` عند الحاجة | لا يتغير المسار عادة. إذا فُصلت واجهة الاستعادة إلى صفحة مستقلة، أضف `/forgot-password` صفحة static خفيفة تستعمل مكوّن نموذج الاستعادة. |
| 6 | `src/app/globals.css` | تنسيق رسالة الحالة، الرابط، حالة التحميل، وتركيز لوحة المفاتيح؛ من دون تغيير واسع في التصميم. |
| 7 | `src/lib/demo-auth.ts` | استخدم `ActionCodeSettings` بقيمة `url: https://<النطاق-الرسمي>/login?reset=sent` و`handleCodeInApp: false`. يجب أن تكون قيمة النطاق ثابتة من متغير عام مثل `NEXT_PUBLIC_APP_URL`، لا مأخوذة من `window.location` أو مدخلة من المستخدم. |
| 8 | `src/lib/demo-auth.ts` | اضبط `auth.languageCode = "ar"` قبل الإرسال إذا كانت رسالة Firebase العربية مهيأة، أو استخدم لغة المتصفح عند اعتماد لغة متعددة لاحقًا. |

### شكل الدالة المقترح

```ts
export async function requestPasswordReset(email: string) {
  const [{ sendPasswordResetEmail }, { firebaseServices }] = await Promise.all([
    import("firebase/auth"),
    import("@/lib/firebase/client"),
  ]);

  const services = firebaseServices();
  if (!services) throw new Error("استعادة كلمة المرور غير متاحة حاليًا.");

  const appUrl = process.env.NEXT_PUBLIC_APP_URL;
  if (!appUrl?.startsWith("https://")) {
    throw new Error("رابط التطبيق الرسمي غير مهيأ.");
  }

  try {
    await sendPasswordResetEmail(services.auth, email.trim().toLowerCase(), {
      url: `${appUrl}/login?reset=sent`,
      handleCodeInApp: false,
    });
  } catch (error) {
    // يسجل رمز الخطأ داخليًا إن أضيفت مراقبة لاحقًا، لكن واجهة المستخدم لا تكشف وجود الحساب.
  }
}
```

> لا ينبغي وضع Firebase API Secret أو SMTP key أو أي كلمة مرور في هذا التدفق. Firebase Authentication يتولى إرسال رابط الاستعادة. لا ينبغي أيضًا إنشاء مسار `/api/password-reset` لمجرد إعادة استدعاء Firebase من الخادم؛ ذلك يضيف سطح هجوم بلا فائدة في النسخة الحالية.

### إعداد Firebase Console اللازم

| الخطوة | المكان | الإجراء |
|---:|---|---|
| 1 | Firebase Console → Authentication → Sign-in method | تأكيد تفعيل Email/Password. |
| 2 | Authentication → Settings → Authorized domains | إضافة النطاق الرسمي لـVercel أو النطاق المخصص النهائي. |
| 3 | Authentication → Templates | تعديل قالب Password reset: اسم ChriGsm، لغة عربية واضحة، ورابط دعم صحيح. |
| 4 | Authentication → Templates → Customize domain | عند امتلاك نطاق مخصص، ربطه برسائل المصادقة وإضافة سجلات DNS المعروضة ثم انتظار التحقق. [3] |
| 5 | Vercel → Environment Variables | إضافة `NEXT_PUBLIC_APP_URL=https://<النطاق-الرسمي>` في Preview وProduction عند تثبيت النطاق. لا يضاف أي سر. |

### اختبارات القبول لاستعادة كلمة المرور

1. المستخدم غير المسجل يفتح صفحة الدخول ويرى رابط الاستعادة.
2. إدخال بريد صحيح ينتج رسالة عامة في الواجهة ورسالة Firebase تصل إلى البريد المقصود.
3. إدخال بريد غير موجود ينتج **نفس** الرسالة العامة؛ لا تكشف الواجهة وجود المستخدم.
4. رابط البريد يعيد إلى نطاق مسموح وآمن ويكمل Firebase عملية تعيين كلمة المرور.
5. كلمة المرور الجديدة تسمح بتسجيل الدخول، والقديمة تفشل.
6. زر الحساب «إرسال رابط التغيير» يعمل بالبريد الموثق ولا يسمح بإرسال رابط إلى بريد يختاره المستخدم في الصفحة.
7. اختبار الهاتف والكمبيوتر، ولقطة معاينة Vercel ثم الإنتاج.
8. بعد التنفيذ، حذف أزرار تعبئة حسابات الاختبار قبل الإطلاق العام؛ لا يجوز أن تصبح الاستعادة وسيلة لتثبيت حسابات تجريبية معروفة.

## 2. ما يجب أن يتضمنه النسخ الاحتياطي

البيانات الواجب حمايتها ليست Firestore فقط. تحتاج خطة الاستعادة إلى أربع طبقات، لأن استرجاع قاعدة وحدها لا يعيد تشغيل المنصة بالكامل.

| الطبقة | الأصل | هل هو ضمن Firestore؟ | طريقة الحماية |
|---|---|---:|---|
| بيانات الأعمال | `categories`, `services`, `customers`, `orders`, `walletEntries`, `supportTickets`, `auditLogs` | نعم | Firestore Backup أو Export |
| هويات الدخول | مستخدمو Firebase Auth وCustom Claims | لا | قائمة مستخدمين/إجراء استعادة موثق؛ لا تخزن كلمات مرور |
| الصور | أصول Cloudinary ومساراتها | لا | نسخ/استعادة Cloudinary أو تصدير سجلات الأصول؛ لا تعتمد على Firestore وحده |
| التطبيق | GitHub والفرع، Vercel config، قواعد Firestore، وثيقة البيئة | لا | GitHub + توثيق متغيرات البيئة + مراجعة Vercel |

### لا تضع هذه العناصر في النسخ الاحتياطي

- لا تصدّر أو تحفظ API keys أو Firebase Admin private key أو Cloudinary API secret داخل Git أو ملف JSON عام.
- لا تحفظ كلمات مرور العملاء؛ Firebase Auth لا يتيح ذلك ولا يحتاجه تدفق الاستعادة.
- لا تضع نسخ قاعدة بيانات في Cloudinary أو روابط عامة أو داخل مستودع Git.

## 3. خيارات النسخ الاحتياطي: قرار مطلوب قبل التنفيذ

وفق وثائق Firestore الحالية، النسخ الاحتياطي المدار، الاستعادة، وPITR تتطلب خطة Blaze وتدفع حسب التخزين والاستعادة. كما أن التصدير والاستيراد إلى Cloud Storage يتطلبان تفعيل الفوترة وBucket تخزين. [4] [5] [6]

| الخيار | ما يبنى | الكلفة | التعقيد | الاستعادة | متى يختار |
|---|---|---|---|---|---|
| **A — نسخ يدوي دوري بلا فوترة** | إجراء موثق لتصدير البيانات المهمة يدويًا، فحص GitHub/Vercel/Cloudinary، وملف مشفر خارج المنصة | لا يتطلب Blaze للبيانات المحدودة إذا تم عبر تصدير إداري مخصص؛ يحتاج مكان تخزين يملكه المالك | منخفض إلى متوسط | يدوية وأبطأ | بيتا مغلقة أو قبل وصول طلبات وبيانات حقيقية كثيرة |
| **B — Firestore Managed Backups** | جدول يومي أو أسبوعي في Firestore مع مدة احتفاظ، ثم استعادة إلى قاعدة جديدة عند الحاجة | يتطلب Blaze وتكلفة تخزين واستعادة | منخفض بعد التفعيل | قوي ومنظم؛ يستعيد إلى قاعدة Firestore جديدة | الخيار الموصى به قبل الإطلاق التجاري العام |
| **C — Managed Export إلى Cloud Storage** | export كامل/محدد إلى Bucket، مع جدولة وخطة استيراد | يتطلب Blaze وCloud Storage وقراءات/كتابات التصدير | متوسط إلى مرتفع | مرن، لكنه يحتاج تنفيذًا وتشغيلًا أدق | عند الحاجة لأرشيف خارج Firestore أو تحليل BigQuery أو نقل بين مشاريع |

### التوصية العملية

لا يمكن تنفيذ نسخ تلقائي كامل ملتزم بقاعدة **«لا فوترة»** الحالية. لذلك:

1. نفذ **استعادة كلمة المرور الآن**؛ لا تعتمد على فوترة.
2. ابدأ بخيار **A** فقط كحماية انتقالية إذا بقيت النسخة بيتا مغلقة ولا تحتوي بيانات أعمال حساسة كثيرة.
3. قبل الإطلاق العام أو عند أول طلبات حقيقية، اختر **B**: نسخة Firestore يومية لمدة احتفاظ 14 يومًا مثلًا، مع نسخة أسبوعية لمدة 8 أسابيع إذا قبل المالك تفعيل Blaze وضبط Budget Alert.
4. لا أنصح بخيار C في المرحلة الأولى ما لم توجد حاجة فعلية للـBucket أو الأرشفة الخارجية.

## 4. خطوات خيار A: حماية انتقالية بلا فوترة

هذا ليس بديلاً مساويًا لنسخ Firestore المدار؛ هو إجراء منضبط يقلل خسارة البيانات خلال بيتا مغلقة.

1. إنشاء مستند `docs/operations/backup-runbook.md` داخل المستودع. يحدد أسماء المجموعات، وقت النسخ، مكان الحفظ المشفر خارج Git، والشخص المخول بالاستعادة.
2. إنشاء سكربت قراءة فقط `src/scripts/export-operational-snapshot.ts` يستخدم Firebase Admin من بيئة موثوقة ويصدر فقط المجموعات التشغيلية إلى JSON: التصنيفات، الخدمات، العملاء، الطلبات، قيود المحفظة، الدعم، وسجل التدقيق.
3. منع السكربت من طباعة أي متغيرات بيئة أو أسرار، ووضع مسار إخراج خارج المستودع مثل `backups/chrigsm-YYYY-MM-DD.json`.
4. إضافة manifest بجانب الملف: وقت التصدير، عدد الوثائق لكل مجموعة، SHA-256 للملف، إصدار Git، واسم مشروع Firestore. لا يوضع ملف النسخة نفسه في Git.
5. تشفير الملف خارج المستودع بمفتاح يملكه المالك، أو رفعه يدويًا إلى مساحة خاصة يسيطر عليها المالك. لا يستخدم Cloudinary أو مجلد تنزيل عام.
6. كتابة سكربت `verify-operational-snapshot.ts` يقرأ النسخة ويؤكد مخططها وعددها وhash قبل اعتبارها صالحة.
7. إعداد اختبار استعادة **إلى Firebase Emulator فقط** أولاً، لا إلى قاعدة الإنتاج. يثبت أن النسخة قابلة للقراءة وأن المجموعات المطلوبة موجودة.
8. تحديد تكرار مناسب يدويًا: قبل أي دفعة CMC كبيرة، وبعد تعديل مجموعة خدمات حقيقية، ومرة أسبوعيًا خلال بيتا. لا تجعلها مهمة تشغيل آلي زائفة داخل بيئة مؤقتة.
9. توثيق أن Firebase Auth وCloudinary لا يعودان من ملف Firestore: يصدر مالك المشروع قائمة المستخدمين من Firebase Console وإعدادات/أصول Cloudinary على حدة.

### ما لا يفعله خيار A

- لا يحمي لحظيًا من الحذف بين نسختين.
- لا يعيد كلمات مرور Firebase Auth.
- لا يعيد صور Cloudinary إذا حذفت من Cloudinary.
- لا يحقق متطلبات الإطلاق العام في حال وجود طلبات ومدفوعات حقيقية.

## 5. خطوات خيار B: النسخ التلقائي المدار الموصى به قبل الإطلاق العام

### إعداد السحابة

1. يقرر المالك صراحة تفعيل Blaze لأن Firestore Scheduled Backups تتطلبها. لا يتم ذلك تلقائيًا.
2. في Google Cloud/Firebase، يمنح المالك أقل صلاحية لازمة لإدارة النسخ، مثل `roles/datastore.backupSchedulesAdmin`، وليس Owner لمستخدم تشغيلي غير ضروري. [4]
3. إنشاء Budget شهري وAlerts قبل تفعيل النسخ، ثم تحديد تكلفة التخزين المقبولة.
4. فتح Firestore → Database → Disaster Recovery/Scheduled backups.
5. إعداد Daily backup مع retention قصير مناسب للبيتا أو 14 يومًا كبداية. الحد الأقصى الموثق للاحتفاظ هو 14 أسبوعًا. [4]
6. إعداد Weekly backup عند الحاجة مع احتفاظ أطول ضمن الحد، مع العلم أن Firestore يسمح بجدول يومي واحد وجدول أسبوعي واحد لكل قاعدة. [4]
7. تشغيل نسخة أولى ومراجعة ظهورها في قائمة backups قبل اعتبار الإعداد مكتملًا.
8. تسجيل اسم جدول النسخ، نطاق الاحتفاظ، موقع قاعدة `eur3`، وتاريخ أول نسخة في `backup-runbook.md`.

### اختبار الاستعادة الصحيح

1. لا تستعد مباشرة فوق قاعدة الإنتاج. Firestore Managed Backup يعيد البيانات إلى **قاعدة جديدة** لا إلى قاعدة موجودة. [4]
2. أنشئ قاعدة استعادة مؤقتة باسم واضح مثل `restore-drill-YYYYMMDD` داخل المشروع عند أول اختبار، ثم استعد آخر نسخة إليها.
3. تحقق من عدد وثائق المجموعات الحرجة، مخطط الخدمة، الطلبات، الأرصدة، وسجل التدقيق في القاعدة الجديدة.
4. تحقق من أن قواعد Firestore وIAM المناسبة تطبق على قاعدة الاستعادة؛ النسخ لا يعيد سياسات TTL تلقائيًا إذا استُخدمت مستقبلًا. [4]
5. لا توجه موقع الإنتاج إلى قاعدة الاستعادة ضمن اختبار؛ الهدف هو إثبات قابلية الاستعادة فقط.
6. بعد نجاح اختبار الاستعادة، توثيق الوقت المستغرق ونتيجة التحقق ثم إزالة قاعدة الاختبار فقط بعد موافقة المالك، لأن إنشاء/حذف قواعد قد ينطوي على تكلفة عند Blaze.

## 6. خطوات خيار C: أرشيف Cloud Storage عندما يصبح مطلوبًا

هذا الخيار لا ينفذ الآن. إذا طُلب لاحقًا، فالتسلسل البرمجي هو:

1. تفعيل Blaze وإنشاء Cloud Storage Bucket خاص قريب من منطقة Firestore، وليس bucket عام أو Requester Pays.
2. منح Cloud Firestore service agent الدور الأقل على الـBucket، ويفضل `Storage Object Admin` على Bucket النسخ فقط بدل صلاحيات مشروع واسعة إذا أمكن وفق إعداد المشروع.
3. تنفيذ تصدير أولي من Cloud Console أو `gcloud firestore export` إلى مسار زمني مثل `gs://<bucket>/firestore/YYYY/MM/DD/<timestamp>/`.
4. إنشاء job مجدول في بيئة تشغيل دائمة يطلق export فقط، يتحقق من operation status، ويكتب manifest مستقلًا. لا تشغل العملية من جهاز محلي أو sandbox مؤقت وتسمّيها نسخًا تلقائيًا.
5. تطبيق lifecycle policy على Bucket لحذف النسخ القديمة بعد مدة الاحتفاظ المتفق عليها.
6. اختبار `gcloud firestore import` إلى قاعدة اختبار، مع الانتباه إلى أن الاستيراد قد يستبدل وثائق لها المعرف نفسه في الوجهة. [5]
7. توثيق صلاحيات Cloud Storage، وقت الجدولة، retention، وأسلوب إيقاف job عند تجاوز الميزانية.

| الدفعة 6 | استبدال حسابات وبيانات الاختبار | بيئة إطلاق آمنة | لا توجد بيانات دخول مدير عامة أو أزرار اختبار |

## 8. ما أحتاجه منك قبل التنفيذ الفعلي

1. **للاستعادة:** النطاق الرسمي الذي سيستعمله المستخدمون. إذا لم يوجد نطاق مخصص بعد، نستخدم رابط Vercel الحالي مؤقتًا في Preview وProduction، ثم نبدله لاحقًا.
2. **للنسخ:** قرار واضح بين **الخيار A** المؤقت بلا فوترة و**الخيار B** الآلي الذي يتطلب Blaze وتكلفة تخزين. لا يمكن تطبيق B تحت قيد «لا فوترة» الحالي.
3. تأكيد موعد إزالة حسابات الاختبار وأزرار تعبئتها؛ هذه خطوة ضرورية قبل الإطلاق العام وليست تجميلًا.
