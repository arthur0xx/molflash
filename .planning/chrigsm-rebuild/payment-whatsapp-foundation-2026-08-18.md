# أساس الدفع وWhatsApp — 2026-08-18

## حالة الانطلاق

- الفرع العامل: `rebuild/next-firebase` عند الالتزام `144dece`، وشجرة العمل نظيفة.
- يدعم الكتالوج والطلب السعر الخادمي فقط: مسار إنشاء الطلب يقرأ السعر وحالة الخدمة من Firestore ولا يقبل السعر من العميل.
- يستخدم دعم WhatsApp الحالي رابط `wa.me` فقط عند وجود رقم مغربي صحيح في الإعداد العام، ولا يستدعي Cloud API.
- لا يوجد في نموذج البيانات الحالي سجل لوسائل دفع أو عملية دفع أو مرجع تحويل؛ تظهر الطلبات بسعر وحالة تنفيذ فقط.
- لقطة CMC المالك هي نقطة القراءة المركزية، بينما لقطة موظف الطلبات تستبعد قيود المحفظة عمدًا.

## قرارات أمان التنفيذ

| المجال | القرار |
| --- | --- |
| رابط الدعم | رقم عام فقط؛ الرابط لا يحتاج سرًا ولا يرسل رسائل تلقائية. |
| السعر | ينسخ الخادم السعر إلى عملية الدفع عند الإنشاء؛ لا يقرأ السعر أو الطريقة من جسم المتصفح كمصدر حقيقة. |
| المرجع | مرجع فريد مولد خادميًا، عشوائي ومحدد الصلاحية؛ لا يكفي لتأكيد الدفع. |
| الدفع اليدوي | التأكيد والرفض للمالك فقط، داخل Transaction خادمي مع سجل تدقيق. |
| طرق الدفع | مسودات أو وسائل مفعلة فقط؛ الطريقة غير المفعلة لا تظهر للعميل. |
| البوابات | CMI وPayzone تعريفات إعداد معطلة فقط حتى تتوفر أسرار خادمية وWebhook واختبارات sandbox. |
| بيانات البنك | تظهر فقط للعميل بعد اختيار وسيلة مفعلة، وتخزن لقطة التعليمات مع العملية حتى لا تتبدل الطلبات السابقة. |
| الفريق | لا تمنح صلاحية مالية افتراضيًا؛ يدير المالك وسائل الدفع والمطابقة والتأكيد. |
| WhatsApp Business | يبقى معطلًا ما لم تكتمل إعدادات Meta الرسمية والقوالب وWebhook الموقّع. |

## المهمة الذرية التالية

ربط رقم دعم WhatsApp المقدم كرابط مباشر صالح في واجهة العميل، مع اختبار صحة التنسيق وعدم تغيير أي مسار API أو بيانات Firestore.
